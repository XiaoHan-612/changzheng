## 一、一句话

三颗糖、五个人、**两次打听**。你并不知道谁真的撑不住，而"知道"是要拿自己的口粮换的。

| | 旧版 | 这一版 |
|---|---|---|

## 三、这一版是什么

历史锚点（`data/facts.json` · `h_share`）：

> 口粮奇缺，战友互相推让食物、留给伤病员，是大量回忆录中的共同记忆。

那一幕的题眼不是"给谁"，而是 —— **你不知道谁要紧，而"知道"要付代价。**

### 两个资源，不是一个

* **3 颗糖**：给谁、给几颗。
* **2 次打听**：走近一个人，才看得见他的里子。**每次打听 = 你自己少吃一顿**（`detail.cost`）。

### 每个人有两个看不见的值

* `need` 缺到什么程度（3 = 再没吃的撑不到明天）
* `share` 拿到糖会不会掰开分给旁边（1 = 会）

而这两件事**通常不在同一个人身上**——`gateFaces` 硬保证「最需要的那个一定不会分糖」。
于是有两条互斥的好打法：

* 给**最需要的**：稳救一个，但只救一个；
* 给**最会分的**（且不止一颗）：他掰开分出去，一颗糖照顾到好几个人，可那个最需要的就悬了。

### 失败条件

* `selfish` 自留 ≥2 颗 —— **是失败**，分数压到 0.2 以下；
* `miss` 最需要的那个人一颗都没拿到 —— **当场没有任何提示**。结算只写"夜里有人咳嗽"，
  真正的惩罚是**你不会知道自己给错了**（这一条是设计核心，别去"优化"它）；
* `ok` / `good`：覆盖到最需要的，且覆盖比例够高。

### 怎么玩

1. 五张卡只写着"表面"和一句硬撑的话；
2. **走近看看**：翻出一个人的里子（缺几／会不会分），代价是自己少吃一顿；
3. **给一颗**：把糖给出去（一颗也可以给同一个人两次）；
4. **剩下的自己收好** → **这一夜就这样**。

## 六、机制数值（都是调过的，别随手改）

| 项 | 值 | 说明 |
|---|---|---|
| 糖 | 3 | `opts.candies` 可覆盖 |
| 打听 | 2 | `opts.asks` 可覆盖 |
| 人数 | 5 | 固定池每份都是 5 人 |
| `need` | 1–3 | 3 = 撑不到明天；**至多两人** |
| `share` | 0/1 | 会分的 **1–2 人**，且**不能是 need 最高的那个** |
| AI 窗口 | **10000 ms** | `AI_WINDOW_MS`，见第八节 |
| 覆盖比 | need 加权 | 覆盖到的 need 之和 ÷ 全部 need 之和（**不是人头数**） |
| 覆盖到最需要的 | +0.15 | "稳救一个"本身有价值 |
| 自留 ≥2 | 压到 ≤0.2 | 且判 `selfish` |
| 最需要的没覆盖 | 压到 ≤0.45 | 且判 `miss` |

`gateFaces` 是**纯函数**，任一条不满足就返回 `null`：5 人 / 字段齐全 / 长度上限 / need 值域 /
share 值域 / 名字不重 / look 至少 3 种 / need=3 不过半 / 会分的人 1–2 个 / **最需要的不会分糖**。

**为什么闸必须在客户端**：「最需要的 ≠ 最会分的」这条约束 schema 表表达不了（它是集合级约束），
与夜校的 `gateLesson` 同一个思路。

## 七、对照实测（同一份代码，不同打法）

固定名单（池子第 1 份，need = 3,3,2,2,1），0 次模型调用：

| 打法 | 分数 | 结局 | 覆盖 | need 覆盖比 |
|---|---|---|---|---|
| S1 打听两人：最需要的给 1 颗 + 最会分的给 2 颗 | **0.877** | good | 3 人 | 0.727 |
| S2 三颗摊给三个不太缺的（没打听，盲给） | 0.450 | **miss** | 3 人 | 0.455 |
| S3 三颗全给最需要的一个人 | 0.423 | ok | 1 人 | 0.273 |
| S4 最需要的给 1 颗，自己留 2 颗 | **0.200** | **selfish** | 1 人 | 0.273 |
| S5 三颗全给自己 | **0.000** | **selfish** | 0 人 | 0 |
| S6 全给最会分的那个人（3 颗） | **0.877** | good | 3 人 | 0.727 |

* **分出了 4 档结局** → "决策真的分叉了"这件事有数可查；
* S2 是这一局最重要的那一行：**盲给的人覆盖率并不低（3 人 / 0.455），但漏掉了最需要的 → miss。**
  "打听"这件事的价值就在这里，不在覆盖率上。

## 八、AI 用在哪：**10 秒窗口**（本轮最重要的口径）

### 原则（定了就别改）

**AI 不许让玩家等。** 模型有 **10 秒**机会；超过就用作者写好的固定内容。

### 为什么是 10 秒：实测数据

| 调用 | 输出 | 实测耗时 |
|---|---|---|
| 网关极简探测（`npm run check:glm`，26→197 tokens） | 197 tokens | **5.3 s** |
| `candy_scene`（开场一句） | 28 字 | **38.7 / 37.0 / 19.2 s** |
| `share_judge`（判词 + effects） | 约 100 字 | **60.5 / 63.7 / 52.9 s** |
| 旧 `share_faces`（当场现编 5 个人，已废） | 2368 tokens | **63.8 s** |

**关键结论：时间几乎全在模型的隐藏推理上，与输出长度无关。**
输出只有 28 个字的那条也要 38 秒，把 prompt 和输出压短**救不回来**。
同网关极简探测只要 5 秒，所以这不是网络问题。

另外实测到过一次 `share_judge` **「模型返回空 JSON」** → 触发重试 → 单次变 63.7 秒。

**结论：在这个网关上，"把叙事 prompt 写短一点让它变快"是做不到的。只能不让玩家等它。**

### 落地方式

| 环节 | 内容 | 是否等模型 |
|---|---|---|
| 出五个人 | **固定池**（作者手写 6 份，逐份过闸） | 不等 —— 开局 **24–56 ms** 进 play（原来是 60 s） |
| 开场一句氛围 | 作者那句立刻在；模型 10 秒内回来就换掉 | 不等 |
| 分数 / 结局 / 谁拿到了 | 作者算 | 不等 —— 点确认到 done **41–45 ms** |
| 判词 | `FIXED_JUDGE[outcome]` 立刻上屏；模型 10 秒内回来就顶掉（并带回 `effects`） | 不等 |

`detail` 上带两个字段给接线方看：

* `judgeFrom`：`'fixed'` / `'model'` —— 判词最终是谁写的；
* `aiPending`：10 秒窗口是否还开着（窗口关了会置 `false`）。

### 两个短时刻的实现

* `candy_scene`：拿"今天做过的事"写一句营地氛围，**只写景与姿态、不写人名、不提糖怎么分**；
* `share_judge`：`operation.type === 'sugar'` 那条分支，口径是
  **只按玩家实际知道的信息说话**（没打听过的人，不许写出玩家不可能知道的事）；
  `miss` 时要写"没有当场揭破"的收场 + 一行 `late_line`（第二天才被随口提起的一句话）。

`share_judge` 那条 prompt 里**故意不要 `items[]`**（旧设计遗留的"逐条写五个人的反应"）：
又长又容易把 token 撑满触发空返回，而那五个人的信息结算屏上本来就有卡片。

### 客户端 abort 之后

`decideWithin` 掐断请求后，**服务端那一调还会跑完并落日志**（清不掉）。
所以从 `logs/ai-calls-*.jsonl` 里数调用次数时，会看到比玩家实际"用到"的更多。

## 九、踩过的坑（这一轮最值钱的部分）

### 1. `status.innerHTML = ...` 把刚加的两行**清成了游离节点**（P0，测试抓到）

`start()` 里原本写 `status.innerHTML = '这五个人你都见过…'`，而 `status` 下面挂了
`hintLine / resLine / judgeLine` 三个子元素。`innerHTML` 一赋值，**子元素全被销毁**，
之后往 `resLine` / `judgeLine` 里写什么都看不见 —— 写得进去，屏幕上永远是空的。

定位方式：把容器子树打出来，`<div class="smini6-status"> "…"` **一个子元素都没有**，当场现形。
（如果只测"值有没有写对"，这条永远抓不到 —— 变量里的值是对的。）

**规矩**：一个容器里挂了子元素之后，任何地方都不许再写它的 `innerHTML` / `textContent`。

### 2. 只给 `fetch` 传 `AbortSignal` 的"超时"**不够硬**

第一版 `decideWithin` 只靠 `ac.abort()`。测的时候那个假接口**无视 signal**，
于是本该被掐断的调用在 12 秒照旧回来，把固定判词顶掉了 —— 断言当场报红。

改成**计时器与请求赛跑**（`Promise.race`），到点 resolve(null)：
上限是客户端说了算，不依赖底层肯不肯听话。

### 3. `:not(.smini6-glow)` —— 通配选择器和光晕**打成平手**

`.smini6-wrap > *` 与 `.smini6-glow` 的特异性都是 `0,1,0`，谁在后面谁赢。
它把光晕的 `position:absolute` 覆盖成 `relative`，光晕当场占掉 320px，
**把五张卡全挤出可视区**（实测 `elementFromPoint` 命中 0/5）。
→ 必须写成 `.smini6-wrap > *:not(.smini6-glow)`。

### 4. CSS 注释里的反引号会**提前闭合模板字符串**

样式是塞进 `s.textContent = \`...\`` 的，注释里写了个反引号包起来的选择器 → 整个模块
`SyntaxError: Unexpected token '*'` → 动态 import 失败 → 玩法根本加载不出来，
表现却是"按钮解析到了却被 detach"，极易误判。**CSS 注释里不要用反引号。**

### 5. 调试台的 `select()` 会清空 `board-body`

它跑在 `load` 之后（模块里有多个 await），会 `board-body.innerHTML = ''`。
注入测试容器**必须等 `#mini-host` 出现之后**，否则注入的容器会被当场删掉。

### 6. 调试台一打开就**自动跑列表里第一个玩法**

那个玩法会真调模型（几十秒）。专项测试要在 `addInitScript` 里把 `/api/decide` 挡掉，
并且**等到 `#mini-host` 再注入**。

### 7. 断言必须**撤掉修复跑一遍**

C2 那条「慢接口下仍是固定判词」写完是绿的。把 `AI_WINDOW_MS` 临时改成 `60000`
（等于没有上限）再跑 —— 它当场报红（`judgeFrom=model`）。恢复 `10000` 再跑，回绿。
**没做过这一步的断言，不能算写了。**

## 十三、这个仓库的几个坑（与《弯针成钩》那份相同，列在这里免得翻文档）

* 浏览器类用例硬编码 `channel: 'chrome'`，**本机没有 Google Chrome**；
  用 `executablePath` 指到 `%LOCALAPPDATA%\ms-playwright\chromium-1223\chrome-win64\chrome.exe`。
* `runtime-config.json` 的优先级**高于** `.env`。现在它是 `{}`（不覆盖），
  一切走 `.env` 里的比赛网关默认值；游戏内「设置」面板写的是它。
* `/api/decide` **成败都返回 HTTP 200**，错误只体现在响应体的 `source` 与 `logs/` 里。
* Bash 里 PATH 是空的，跑 node 前要先 `export PATH=...`。
* 另外：`logs/` 里可能出现**不属于当前测试**的调用记录（比如你自己开着页面在玩），
  数调用次数时别把它当成测试泄漏。
