## 一、旧实现薄在哪（重做的理由）

旧版是**"限时点门板 + 5 次金区落板"**，搭完就结束。它漏掉的恰恰是史实里最要命的那半截：

| # | 问题 | 后果 |
|---|---|---|
| 1 | **"夜架晨拆"根本没出现** | 于都河渡口是**傍晚架、天亮前拆**——拆是为了不被敌机发现。旧版搭完就完事，"天亮前拆完"这个压力源为零。 |
| 2 | 门板是无限的 | 史实是**群众拆门板、床板送来**。旧版点一下就有，没有"东西会不够"这回事。 |
| 3 | 没有"船"这个稀缺物 | 史实是 5 条船横排、8 处中流靠船，其余只能铺板排。旧版的"金区落板"和船无关。 |
| 4 | 没有水流 | 下锚要**掐稳流窗**（水稳的时候锚才咬得住）。旧版没有水流这个概念。 |

## 一·补、本轮修掉的两个 bug（都是"玩法其实打不动"级）

### ① 段行每帧重建 → 自动化一段都点不进去（真人却没事）

`renderSegs()` 挂在 `sync()` 里，而 `sync()` **每帧都跑** → `segRow.innerHTML = ''`
**每秒重建 700+ 个按钮节点**。真人点击落在指针下的活动节点上没问题，
但脚本侧 `page.click` 拿到的节点**下一帧就被换掉**：

```
点 seg#5：ERR:page.click: Timeout 3000ms exceeded.
```

→ 桥一段都搭不上 → 三局全 `exposed`、C4/C5/C6 全红。
**修法**：段行加签名守卫，只在 `segs / phase / alarmSeg / anchorSeg` 真的变了才重建
（和面板"只在取整值变化时重写"同一条道理）。修完：点第 6 段 → `state=anchor anchorSeg=5`、船 4 板 3 ✓。

> 排查手法记一下：`page.$()` 点不到时**先别怀疑层级遮挡** ——
> 在页内 `elementFromPoint` 打一行命中结果。能命中（本例 `行中心命中=seg1`）就说明不是遮挡，是节点在被换。

### ② 搭满即渡的判定漏了"铺板排铺满"这条路径（软锁，模拟抓到的）

"桥搭满 → 进渡河"的判断原来只写在 `doAnchor()` 里。若**最后一段是用铺板排铺满的**，
永远进不了 `cross`：桥搭满了、按钮还在、天却照走。已把判定移进帧循环的 `rig` 分支，覆盖任何完成路径。

**修完的正确打法实测**（诊断脚本逐秒打点）：
挂灯 → 浅滩 4 段铺板 → 中流 5 段下船掐窗下锚 → 中流 3 段铺板 → 渡河遇警加固 → 天亮前拆完，
**`score 0.75 / pass`，实耗 55s，断 1 次，未还门板 0。**

## 一·补二、本轮修掉的第三类问题：**这一局在数学上不可能通关**

`qa-pontoon.mjs` 全量跑出来 6 项红（B1/B1b/B2/B4/C7/C9）。逐项看像六个毛病，
根子只有两个，而且都不是"代码写错"，是**设计算术不成立**与**驱动一旦点空就放弃**。

### ① 材料经济算错了：正确打法必沉

把数字摊开就一眼：

- 搭满 12 段要 **15 块板**（4 浅滩×1 + 5 船×1 + 3 中流板排×2）；
- 真正会被水冲开的段，只有**中流那 3 段板排**（浅滩板排稳、掐准窗下锚的船是 `S` 也不晃）；
- 而一段报警**要么被加固**（→`R`，出局）、**要么过窗没加固**（→塌掉，也出局）
  → 所以全场报警次数 **≤ 3**，最坏情况要 **3×2 = 6 块加固料**；
- 原来 `PLANK_CAP = 18`，`18 − 15 = 3` —— **只够加固一次半**。

于是无论怎么打，第 2 次报警必然看着它塌。更糟的是原设计是"**搭满即自动渡河**"：
玩家越手快、越早把桥搭完，手里越是一块余料都没有 —— 手快反而吃亏，而且**玩家没有杠杆**。

**修法两条**（都记在文件常量区的注释里）：

| 改动 | 从 | 到 | 为什么 |
|---|---|---|---|
| `PLANK_CAP` | 18 | **24** | 24 − 15 = 9，够最坏情况 3 次加固还有富余 |
| `PLANK_ARRIVE_EVERY` | 5 | **4** | 到货快一点，等料的时间从 ~20s 缩到 ~12s（别把夜色全吃掉） |
| 到货上限判断 | `arrived*2+4 < CAP` | 只看 `planks < CAP` | 原来那个式子会提前断供（9 批之后就不送了） |
| 渡河触发 | 搭满**自动** | **新动作「部队上桥」** | 玩家才有"现在就上桥，还是再等两批门板"这个决策 |

**新动作的契约**：`data-mini-action="cross"`（扛 `Space`）；桥没搭完时 `disabled` 且
**不挂** `data-mini-action`（所以 A7 的"起手可点元素 = 15"不变，搭满后才 +1 → 16），
只有 `allBuilt` 翻转的那一帧才重画一次动作行（节点不抖）。

> 这一改把**第三个真决策**装回来了：留料 = 稳但吃夜色，不留 = 抢时间但第一段报警必塌。
> 原来那句"搭满即渡"其实等于没有决策 —— 手快只有坏处。

### ② 驱动"点空一次就放弃" → 桥永远搭不满，看着像玩法崩了

`playProper()` 原来写死顺序（浅滩 → 5 船 → 3 板排），其中 `boatTo()` 只**点一次**：
门板是陆续到的，某一步手里不够时那一次点击在游戏里就是**空操作**（`fbEl` 只提示"船或门板不够了"），
`boatTo` 见 `miniState !== 'anchor'` 就 `return false` → 外层 `break` → **再没搭过一段**。

症状极具误导性：B1/B1b/B2/B4/C7/C9 **六项一起红**，其中 C9 的实得状态序列是
`rig/done/anchor` —— **`cross` 从头到尾没出现过**，这一条才是真线索：
桥没搭满 → 进不了渡河 → 三局全部 `exposed`、`断0`、`B4 分叉` 自然也是 0.2 vs 0.2。

**修法**：驱动改成**自适应**——每一轮重看"还缺哪段、手里几块板 / 几条船"，够就点、不够就等；
先浅滩（1 板）→ 中流船段（1 板+1 船）→ 中流板排（2 板）。修完 `pass`。

> 教训：**玩法 QA 红了先分清"玩法坏"还是"驱动坏"**。
> 一个"断掉整条链"的提前 `break`，能让一个健康的玩法看起来六处同时烂。
> 判据是**状态序列**：序列缺哪一环，就往哪一环的上游找。

## 一·补三、再修一条：**"不加固"这条失败线原来是掷骰子**

材料经济调平之后 B1 绿了，B2 还红 —— 而且红得很怪：**「未结算」**（不是 `exposed`、不是 `pass`）。
`未结算` + C9 状态序列里出现了 `dismantle`，说明这一局**不加固也把部队送过河了**。

### ① 为什么"不理报警"竟然能过桥

看 `frame()` 里的报警逻辑：

```js
if (cross >= waveNext) {
  waveNext += CROSS_WAVE;
  if (alarmSeg < 0) {                       // ← 报警期间**不掷骰**
    const risky = [...所有晃段...];
    if (risky.length && rnd() < WOBBLE_RISK) { alarmSeg = ...; alarmLeft = ALARM_SEC; }
  }
}
```

- 报警必须等上一条**解决**（加固→`R`，或者过窗→塌）之后才能再来一条；
- 一次渡河只有 **约 11 秒**（`CROSS_RATE = 0.092`），而一条"报警 + 4 秒窗口"就吃掉 **4.9 秒**
  （窗口 4.0s ＋ 报警只是等待期间 waveNext 照走的 ~0.9s）；
- 所以全场只够掷 **~3 次** 骰，`P(至少 2 次报警) = 1 − 0.58³ − 3·0.42·0.58² ≈ **0.38**`
  → **"不加固"有六成概率照样过桥**。

**玩家看得见的失败条件不能是掷骰子。** 而且这一条不修，B4 的"分数分叉"也一起塌
（正确 0.85 vs 沉物资 — 根本拿不到第二个数）。

### ② 修法：每次判定必报一段（报哪一段随机）

```js
if (risky.length) {                          // 去掉 `rnd() < WOBBLE_RISK`
  alarmSeg = risky[Math.floor(rnd() * risky.length)];   // 随机性保留在"报哪一段"
  alarmLeft = ALARM_SEC;
}
```

于是**报警次数 = 晃段数**，账变得可算、可复现：

| 打法 | 晃段数 | 点名要的加固料 | 结果 |
|---|---|---|---|
| 5 船全给中流 + 都掐在窗里 + 3 段板排 | 3 | 6 板（封顶 24 有 9 板余量） | 加固三次 → 过桥 |
| 有 1 条船没掐进窗（`W`） | 4 | 8 板 | 勉强（1 断可容） |
| 船铺到浅滩上（中流多一段板排） | 4 | 8 板 | 同上，越来越紧 |
| **不加固** | 3 | 0 | **第 2 次报警过期 = `sunk`（确定）** |

配套 QA：B1 加 `B1c 这一局真的报了 ≥3 次警`（防随机性偷偷回来）、
B2 的结果与原因一起断言（`sunk` **且** 报警 ≥2 次）——
免得"只报了一次警→没断→跑到拆桥→未结算"这种状态被误读成玩法坏了。

> 顺带：`WOBBLE_RISK` 这个导出常量已删除（全仓只剩这个文件用）。
> 以前那句"42% 冲开概率"在 §四 的虚构声明里也一并去掉了。

## 三、这一版是什么

### 四个阶段：`rig → anchor → cross → dismantle → done`

1. **rig（搭）**
   - 12 段桥面：`0,1,10,11` 是**两岸浅滩**（`isShallow`），其余 `2..9` 是**中流**。
   - **只有 5 条船**（史实 800 条，局内是配给）。下船：**1 船 + 1 板**，占住一段中流。
   - 下船后进 `anchor`：**掐稳流窗**下锚 —— 窗口内 → `S`（船稳）；窗口外 → `W`（船晃，`wobble`）。
   - 门板排：浅滩 **1 板**/段（稳）；中流 **2 板**/段（**晃**，过部队时可能被冲开）。
   - 搭满**不自动**渡河：要点「**部队上桥**」（`data-mini-action="cross"` / `Space`）。
     这一刻是决策 —— 门板还在陆续送到，先走还是再等两批？（见 §一·补二①）
2. **anchor（下锚）** —— 稳流窗 `FLOW_WIN = [42,58]`；**挂马灯**后放宽到 `[32,68]`。
3. **cross（部队过桥）**
   - `CROSS_RATE = 0.092`/s（约 11 秒过完）。
   - 每过 `CROSS_WAVE = 8.5%` 的桥面判定一次：从所有**晃段**里挑一段**报警**（红圈闪 4 秒）。
     ⚠️ 2026-09-16 之前这里是 `WOBBLE_RISK = 42%` 的**随机**报警 → **失败线不可靠**：
     报警期间不掷骰，而一次渡河只有约 11 秒、一次"报警+4 秒窗口"就吃掉 4.9 秒 → 全场只够掷 ~3 次骰，
     `P(≥2 次报警) ≈ 0.38` —— **"不加固"有六成概率照样过桥**。现已改成"每次判定必报一段"
     （报哪一段仍随机）→ 报警次数 = 晃段数，账一目了然。
     见 §一·补三①。
   - 4 秒内点「加固」（**2 块门板**）→ 该段变成 `R`（**永久不再晃**）。慢了 → **断**（`breaks + 1`，该段塌掉，队伍退回几步）。
   - **断 2 次 = `sunk`**（物资和门板一起沉）。
4. **dismantle（拆）** —— 一段一段点，每段 `DISMANTLE_SEC = 0.85` 秒；全拆完 → `pass`。

### 两个失败条件

| 结局 | 触发 |
|---|---|
| `sunk` | 桥被冲开 2 次 |
| `exposed` | 夜到 100%（`NIGHT_SEC = 110` 秒）还有段没拆完 |

### 常量表

| 常量 | 值 | 含义 |
|---|---|---|
| `SEGS` / `BOATS` | 12 / 5 | 桥段数 / 船只配给 |
| `PLANK_START` / `PLANK_ARRIVE_EVERY` / `PLANK_ARRIVE_N` / `PLANK_CAP` | 4 / 4s / 2 / 24 | 门板：起手 / 到货间隔 / 每次到几块 / 封顶（**24 是 2026-09-16 从 18 调上来的，见 §一·补二①**） |
| `NIGHT_SEC` | 110 | 一局的夜长（17:30 → 06:30 压缩） |
| `FLOW_SPEED` / `FLOW_WIN` / `FLOW_WIN_LAMP` | 0.62 / [42,58] / [32,68] | 对位流速 / 稳流窗 / 挂灯后的窗 |
| `CROSS_RATE` / `CROSS_WAVE` / `ALARM_SEC` | 0.092 / 0.085 / 4.0 | 渡河速度 / 每过多远判一次冲开 / 加固窗口 |
| `REINFORCE_COST` / `BREAK_MAX` | 2 / 2 | 加固花费 / 断几次沉 |
| `DISMANTLE_SEC` | 0.85 | 每段拆多久 |

**经济账（QA 会核）**：搭满全桥 = 浅滩 4×1 + 中流 5 船×1 + 中流 3 板排×2 = **15 板**；
把 3 段晃的全加固 = **6 板**；合计 **21 板 ≤ 封顶 24** —— 刚好够，还剩 3 板容错。
**但这 21 板不是同时到手的**：门板每 4 秒才到 2 块，所以**必须先把桥搭完、再等两批门板攒够加固料，
才让部队上桥**（见 §一·补二①）。不等就上桥 = 手里一块余料都没有，第一段报警只能看着它塌。
乱花（船铺到浅滩上、或者料不够就上桥）照样断 —— 这就是这一版的资源压力。

**AI：游戏内 0 次模型调用**（用户原话：浮桥把体验做好就行，API 无所谓）。

## 四、史实锚点

`data/facts.json · h_depart`（act0）：

> 1934 年 10 月，中央红军主力 8.6 万余人从江西于都等地出发，开始长征。
> **于都河渡口夜渡，群众拆门板、床板搭浮桥支援。**

→ 三件事直接落进机制：**门板是群众陆续送来的**（`PLANK_ARRIVE_*`）、
**夜里架、天亮前拆**（`NIGHT_SEC` + `dismantle` 阶段）、**船工的马灯**（`lamp` → 稳流窗放宽）。
"800 条船"的史实规模在局内被压成 5 条配给，是为了让"船不够"成为决策。

**虚构声明**：对位流速、稳流窗区间、局内 110 秒夜长都是互动化设计。

## 六、接线（怎么接回主线）

1. `public/js/minigames-registry.js`：热点 `bridge` 这条不在注册表（`bridge` 属于 `STORY_MINIGAMES`），
   所以接线时把它从 `minigames-story.js` 挪进注册表并指向 `runPontoonNight`。
2. `public/js/minigames-story.js`：删旧 `runBridgeBuild` 及其 `ensureStyle/palette` 里只服务它的部分。
