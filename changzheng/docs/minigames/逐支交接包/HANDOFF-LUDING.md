## 一、v1 为什么不算数

v1 做的是「曳光预警 0.85 秒 → 按住 S 贴链 → 中弹 +1 → 满 3 次坠江」。
它本身不算差，问题是**它和同批的陡坡 / 浮桥 / 担架是同一套骨架**：

| 四支 | 皮 | 骨 |
|---|---|---|
| 陡坡 v1 | 雪坡救人 | **0.8 秒窗口 → 按一下 → 扣一格 → 扣满 M 次失败** |
| 泸定 v1 | 铁索桥上中弹 | 0.85 秒预警 → 按住贴链 → 中弹 +1 → 满 3 次坠江 |
| 浮桥 v1 | 下锚掐流窗 | 掐流窗 → 按一下 → 桥被冲开 +1 → 满 2 次失败 |
| 担架 v1 | 听声卧倒 | 引擎声起 → 0.85 秒后扫射 → 按一下卧倒 → 血尽失败 |

用户的判语是：**四支拆开看是四个题材，合起来是一个人。**
所以 v2 的硬要求是"换骨架"，不是"换皮"。

## 三、v2 是什么：两个不可逆的稀缺资源 × 一条时钟 × 一个换挡税

**没有预警窗口，没有"按一下躲"。** 你不是在躲子弹，你是在**排班**。

### 三笔账

| 账 | 是什么 | 收益 | 代价 |
|---|---|---|---|
| **姿态**（连续量） | 按住「贴链匍匐」⇄ 松开「直起身冲」 | 贴链 0.95 m/s；冲 3.05 m/s | 贴链折人 ×0.25；冲折人 ×1.85；**换姿势要站住 0.75 秒**（这半秒按 ×1.20 算暴露） |
| **6 块门板** | 把**你脚下这一段**铺成板面 | 板上折人 ×0.10 —— 又快又安全 | 铺的 2.5 秒你**停下**，三连在火力下扛板（按 ×0.18 算）；**102 米只有 6 段拿得到** |
| **3 发掩护** | 停火 5 秒 | 折人归零，可以放心冲 | 只有 3 发、**不能叠加**（生效期间按钮变灰）；15 秒买不了整局 |

### 两条失败线

| 结局 | 触发 | 为什么这样设计 |
|---|---|---|
| `fire` | 78 秒内没过完 | 一路贴链要 **107 秒** —— 史实里东桥头浇了煤油，时间本身就是敌人 |
| `wiped` | 折满 **22 人** | 一路直冲约 **28 秒折光**（过到 87 米）—— "他一个人冲过去了"不是胜利 |

### 与陡坡 v3 的关系：**刻意做成镜像**

- 陡坡：按下去 = **用力**（危险、会绷断，靠**松手**活下来）；胜负手是"别绷断"。
- 泸定：按下去 = **贴住**（安全、但慢，靠**松开**抢时间）；胜负手是"拿多少人换多少秒"。

按键动作相反、胜负手相反。所以"按住某个键"这个共同元素**不是同一个机制**。

### 6.1 本轮被 QA 逼出来的两个手感缺陷（D3 / D8）

QA 头一次跑是**【有红】 5 项**。其中 3 项是**断言自己写错了**（A11 拿 `< 半桥` 判"必须挑"，
而设计是 `≤ 半桥`；C2 想在 0.7 秒的窗口里等到整数折人，而第一段火力 0.13 人/秒要 7.7 秒才折 1 个；
F11/F12 冲到 95 米时人已经折光、板屏 `done`，掩护按钮按不动）。
另外 2 项是**真缺陷**，而且都是靠读 `miniHurt` 的**比值**读出来的 —— 两条都表现成 `×1.20`，
而 ×1.20 正是 `SWAP_HURT`：

| 现象 | 根因 | 改法 |
|---|---|---|
| 铺完板的那一瞬折人率是 ×1.20 而不是 ×0.10 —— **板刚落地就白挨枪** | `step()` 里 `layLeft>0` 那一支**不推换挡计时**，于是"扛板前挂起的换挡"冻在 2.5 秒里、铺完之后接着扣 | `doLay()` 开头把在途换挡**就地结清**（`swapLeft = 0; stance = wantStance;`）—— 扛板本来就走不了 |
| 松手之后角色先蹲回旧姿势、再罚站一次，实际站住 **1.5 秒** | 换挡一开始就把 `stance` 定成旧目标；中途改主意只能等本次换挡结束，再排**第二次**换挡 | 换挡期间每帧 `stance = wantStance`（落到"最后要的那个姿势"），不再叠第二次 |

两处都只动"改主意 / 压边"的边角，**火力表一个字没改**：改完重跑 sim，八套打法结局与分数一字未变（见上表）。

> 这两条只有"读连续量"才抓得到：老骨架（预警 → 按一下 → 扣 1）在 dataset 里**没有 `miniHurt` 这个字段**，
> 这类缺陷在它身上根本不存在、也无从测起。所以 D3 / D8 既是骨架判据，也是一张回归网。

### 6.2 环境坑（不是玩法的事，但会把验收整条卡死）：`browser.close()` 会挂住，而且掐不掉

本机 `browser.close()` 不只是"慢" —— 实测**连 `setTimeout(() => process.exit(0), 500)` 这个硬退都不发火**：
脚本已经打完所有输出，进程仍能挂 40 分钟不走（已经攒了一批 `qa-grab` / `shot-grab` / `sim-luding` 僵尸进程）。

后果很隐蔽：`node sim.mjs && node qa.mjs` 这种串联**永远走不到第二段** ——
看着像"QA 卡死了"，实际是上一段的进程根本没退。

**三个泸定脚本已改成不走 `close()`：**

```js
try { browser.process()?.kill('SIGKILL'); } catch { /* 已经没了就算了 */ }
process.exit(0);
```

（chrome 子进程随父进程一起走 —— 实测退出后 chrome 进程数为 0。）
但 `qa-grab` / `shot-grab` / `sim-grab` / `qa-gomoku` 等脚本**还是老写法**，下次跑它们要留意同样的卡死。

## 七、调参口径（为什么是这张火力表）

火力表不是拍脑袋的，是照着**三条硬要求**倒推的（都能量、都实测过）：

1. **只求稳必输**：`BRIDGE_M / CLING.spd = 107.4s > TIME(78s)` → 贴链这条线死在时限。
2. **只求快必输**：`RUSH.hurt/RUSH.spd × SEG_M × ΣFIRE = 32.2 人 > 22` → 直冲这条线死在折人。
3. **光靠掩护也过不去**：3 发掩护全打出来换直冲，仍要折 **25 人 > 22** → **门板是硬需求**，不是可选项。

这三条同时成立，玩法才有唯一解的形状：**板留给火力最强的那几段，掩护用来换时间和命，姿态负责把剩下的账平掉。**

早一版（`FIRE` 末段 1.31、`PLANK_HURT = 0.13`）实测"正解折 11 人"，太苦；把火力表整体调硬一档、
同时把板的让利给足（×0.10），正解才落到"折 5~7 人"这个像话的区间。

## 十、已知欠账

- **`TIME = 78` 是"局内秒 = 史实 40 分钟"的压缩**，和主线节奏的换算还没和策划对齐。
- 姿态/门板/掩护的判定**没有单测**（`minigames-luding.js` 的 `step()` 是纯状态推进，
  但要抽成纯函数得先把它和 DOM 解耦），目前只由 QA 的真按键与真点击覆盖。
- **火力表是静态的**：没有"敌人被压制后修正火力"这类反制。想过一版"每用一发掩护、此后基线火力 +6%"，
  能让"掩护什么时候用"再多一层账，但会让 QA 的口径变多，先记在这里。
- 画作右缘（x > 1246）会带出一点点水彩纸边，取景框压到 1246 就为止了 —— 再往右会明显穿帮。
