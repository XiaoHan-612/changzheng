## 第三轮：玩法扩展设计 + 修掉减动效下玩乐板点不动的缺陷
（用户请求："玩法上有没有精进的？现在对话居多，能不能加小游戏，单独开发再嵌进去"）

### 先记一个反复踩的坑：验证必须证明"断言能失败"
本轮差点报出一个**假 P0**。我最初用"手工注入 DOM + elementFromPoint"判定板屏被遮挡，
在默认动效下测出"被 board-bg 挡住"，于是当成"所有用户都点不动"。
实际用真游戏流程复测才发现条件性：
- 入场动画 `sheet-rise` 的 `fill-mode: both` 会在板身留下 `transform: matrix(1,0,0,1,0,0)`
  （**单位矩阵，但语法上非 none**）→ 板身成为层叠上下文 → 恰好压在背景层上 → 可点。
- **只有 `prefers-reduced-motion: reduce` 时**动画被整个去掉、`transform: none`，板身退回 static
  → `.board-bg`（absolute）吞掉全部点击 → **8 个玩法一个都点不动**。

**教训（重要，下次直接照做）**：
1. 判定"能不能点"必须在**真游戏流程**里测（走 `window.__czScreens.mini(name)` 钩子），
   不要手工注入 DOM——手工注入没有入场动画的 transform 残留，会得出与真实相反的结论。
2. 写完断言必须**临时撤掉修复跑一遍**，确认它真的会红。本轮就是这么发现
   "按默认动效跑永远不会红"的，于是把断言改成在 `reducedMotion: 'reduce'` 条件下跑。

### 原版的问题（重做的理由，已写进文档）
主线 `runFishing`（`minigames.js:52`）= 抛竿 → 等一个漂相窗口 → 窗口内按一次空格 → 给分，重复 3 次。
**玩家全程只有 3 次单点操作**，没有持续操作、没有博弈 → 本质是一道反应力小测。

### 重做版：三层结构
- **识别层**：漂相三档（晃 = 假口空钩 / 沉 = 真口 / 黑漂 = 大物、钩得牢线不易伤）。
- **搏鱼层**（核心）：按住收线→张力涨、松手→落；**甜区 45–82 收线效率最高**（太松线拉不直、太紧不敢发力）；
  鱼周期性**挣扎**，此时若还在收线则张力 ×2.4 暴涨（半秒必断），松手反而落得更快。
  → 正解 = **它冲时松手、它喘时收线**。顶 100 撑 0.55s 断线、松到 8 撑 1.4s 脱钩、绷过 90 磨线扣分。单竿限时 40s。
- **收束层**：鱼的体力（被应激与收线消耗）耗尽 → 力竭 → 挣扎停止、收线 ×2.2。
- **叙事嵌合**：这套机制就是老班长的做法——**不跟它硬拼，跟它耗**。

### 三组对照实测（"它到底是不是游戏"的证据）
| 组 | 操作 | 结果 |
|---|---|---|
| smart | 鱼一挣扎就松手 | 三竿全上岸 · 10.8 / 12.5 / 15.0 秒 · 线**完好** |
| dumb | 一直按住不放 | **2.2 秒断线** · 张力峰值 106 |
| greedy | 贴着断线边缘收（张力 88+） | 能上岸，但更快磨线 |

### 探针逼出来的三个修正（都是真问题）
1. **力竭逻辑写反了**：原式 `gap *= (0.55 + stamina/满 * 0.65)` → 体力越低间隔越短、挣扎越频繁（与设计相反）。
   改为 `gap *= (1 + (1 - vigor) * 1.6)`，并加"体力 ≤ 0 直接停止挣扎"。
2. **老鱼打满 40s 超时**（收线速率抵不过外冲）→ `reel` 21→30、`rush` 下调、`exhaustBoost` 1.9→2.2。
3. **超时误归类为 `slack`** → 新增 `timeout` 类别，detail 与结算文案都补上。

### 关键经验（下轮直接用）
- **时序玩法必须暴露"决策所需的状态"**，否则自动化写不出来。本支新增：
  `miniTension / miniDist / miniStamina / miniStruggle / miniBite / miniRod`。
  契约只强制 `mini` + `miniState`，但这是写自动化的前提。已写进 MINIGAMES.md §工具三。
- **"证明它能输"比"证明它能赢"更有说服力**：用户质疑"是不是真游戏"时，
  `一直按住 → 2.2 秒断线` 这条比任何描述都管用。以后做玩法都配一组"错误操作的对照组"。
