### 一个重要经验（给后面所有玩法）
- **"金色钩"和"火苗"是同一个颜色族，光靠色比分不开**（金色本来就是炉火色，火苗 mid→core 渐变会落进同一窗口）。
  实测"满画面扫金"在**什么都没做**时也能数出 1216 个，包围盒 `179,280 → 319,324` 全是炭盆的火。
  **判据必须"色比窗口 + 取样框"两条一起用**：色比 `g/r∈[0.78,0.90] ∧ b/g∈[0.47,0.60] ∧ 够亮`，
  取样框取定妆位钩身上半段 `x 296–352 / y 176–258`（火苗最高只到 y≈266，框底在它之上）。
- 结果：**成品钩 693 个金像素（包围盒 `301,182 → 341,258`），两组对照 0 / 0**。
  而缺陷在的时候读数是 **0** → **这条断言的检出能力是被验证过的**，不是"加了之后永远绿"。

## 用户验收反馈：「画面还行，就是里面的文字有点糊」→ 已修
- **不是分辨率问题，是"设计 px 不等于屏幕 px" + 宋体**。三条叠加：
  1. 画布写死 `canvas.width = 720*DPR`，而元素被 CSS 压到 **570 宽**显示
     （`--panel-w:620px` 减左右 `--sp-5:24px`）→ 缩放 **0.79**，HUD 里写死的 `10px` 只剩 **7.9 屏幕 px**。
  2. 字的栈用的是 `--font-num`，它是 `num, serif, Georgia, serif` —— 数字吃 EB Garamond，
     **汉字落到第二顺位的 serif（Noto Serif SC，宋体）**，8px 上下笔画直接断。
  3. 纸面提示文字 11px + `--ink-2`（纸色最浅褐），对比度也不够。
- 修法（正面修，不是把字号碰运气调大）：
  - **后备缓冲跟着显示宽度走**：`canvas.width = 显示宽 × DPR`，`viewScale = 显示宽 / 720`；
    用 `ResizeObserver` 观察**容器**并加 `lastCssW` 早退防自激。
  - **HUD 字按物理像素定死**：设计字高 `fpx = HUD_PX / viewScale` 反算，上下限 `HUD_FP_MIN/MAX` 防极窄画布撑破排版。
  - 小字专用 font stack：数字仍吃 `num`，**汉字落到 `"Microsoft YaHei" / "PingFang SC" / "Noto Sans SC"`**。
  - 仪表盘由 226/168/124 改成**三列等宽 166 / 间隔 17**（16、199、382，右止 548，避开 578 起的样板框）——字变大后原排布会互相撞。
  - 纸面提示 11→13px、`--ink-2`→`--ink-1`；状态行 13→15px。
- **实测证据**（在 `qa-needle.mjs` 里新加"字号体检"段，用 `ctx.measureText('火')` 真量一个汉字）：
  修复前 `10 × 0.79 = 7.9` 屏幕 px → 修复后 **12.99 屏幕 px**；`ctx.font` 回读确认栈里已是 `Microsoft YaHei`。
- 复跑六种打法：**0.9832 / 0.09 / 0.1 / 0.1 / 0.268 / 0.699**（与修复前完全一致，说明只动了显示层）。
  减动效可点性通过、契约 4/4、页面报错无。

### 顺手改掉的一个断言脆弱点（重要）
- 金色像素的**原始个数会随后备缓冲分辨率变**：同一枚钩 DPR 2 下 421 px、DPR 1 下只剩 100 出头。

## 泥地五子棋重做（第四支，单独开发，未接线）—— 验收全绿 40/40

文件：`public/js/minigames-gomoku.js`（1635 行，id `mud-gomoku`）+ `tests/manual/qa-gomoku.mjs`（722 行）
+ 调试台第 5 分区 + 服务端 `gomoku_move` callType（`server/ai.js` / `schema.js`，schema 单测 19→20 类）。

### 🔴 最重要的一条：**这一版的引擎第一轮是坏的，而且坏得看不出来**
第一轮验收 12 项红。刨到底是一个真 bug：**三档棋力的强弱是反的** ——
`hard 对 easy 20 局只赢 1 局`、`hard 自对自 20 局全平`。根因是旧代码里那段"hard 安全检查"：
它把候选按"对面下完最好的一手有多强"**重排**，等于**只算对面、完全丢掉自己的进攻** →
hard 变成纯挡子机器，两边互堵到棋盘填满，**游戏没有胜负**（平局 0.45 成了唯一出口）。
- 修法：换成**威胁阶梯** —— `我活四 > 挡对面活四 > 我双活三 > 挡对面双活三 > 位置分`。
  杀招判定 `killerRank` 很直接：落完这一手，我有几个"下一手能成五"的点？
  2 个 = 活四/双四（对面挡不住）；1 个 = 冲四；0 个再数"下一手能做出活四"的点，≥2 个 = 双活三。
- **⚠️ 阶梯里绝对不能加"预判性堵对面单个四/单个三"这一层。** 加过（`danger` 权重那版），
  结果是双方都不敢进攻 → hard 自对自 20/20 全平、hard 打不过 easy。**宁可让单个四漏过去。**
- 三档的差别改成**"他看得见多远的杀招"**（easy 不算 / mid 算到四 / hard 还认双活三），
  不是噪声大小 —— 这才是真分层。实测 40 局：mid:easy **27/0/13**、hard:easy **32/0/8**、
  hard:mid **11/4/25**、hard:hard **20/20/0**、easy:easy 18/19/3。

### 平局率高是**固有特性**，不是 bug（追过一轮才承认）
换 11 路盘重测：`hard:hard` 仍然 20/20 全平 → **与盘面大小无关**，是两个都会防的引擎互堵。
所以 A5 的判据从"胜场数"改成**性质**：① 最弱档对中/硬档一场不赢 ② 硬档强过中档且不落下风
③ 硬档与最弱档自对自都必须能分出胜负。**判据取性质、不取数字 —— 引擎一改数字就漂，性质不会。**

### 另外两个只有失败路径/特定帧才暴露的坑
1. **模型写的台词只活几个毫秒**（E8 红）：`afterMove()` 换手时会把状态栏刷成固定嘲讽，
   把 `requestKidMove` 刚写的模型台词**冲掉**。修法：加 `lastSay` 做过渡，
   `afterMove` 里 `lastSay || (band ? ... : TAUNT[...])`。**顺带把 say 暴露成 `dataset.miniSay`**，
   否则自动化只能读 DOM 文本，说不清"是模型的话还是固定嘲讽"。
2. **渗水预告带与"成五结算"抢同一个位置**（D3 红）：`afterMove` 先判胜负，赢了就直接 `return`，
   `schedulePuddle()` **压根不跑** → 那一手没有带子。所以我原来写的
   "有子 + 有水洼 + 有预告带三者同时"**在代码控制流上永远不可能成立**（带子在第 7/11/15 手，
   水洼要下一手才落定）。修法：**拆两帧采样** —— 第 7 手验分类/半格反证/带子可见，
   再走到水洼落定验"水洼真的是发青的"。
