## 本轮修掉的一串**验收脚本（driver 侧）问题** —— 教训已写进 skill

1. **别用 `setInterval` 轮询页面**（`watchStates` 那类）：60ms 一次 `page.evaluate` 会和 driver 抢页面，
   时序一抖就会去点"已经消失的按钮"。→ 状态序列改成在 `read()` 里顺手 `seenStates.add(...)`。
2. **裸 `page.click` 会一直重试到超时**：玩法结算时 `acts.innerHTML=''`，driver 还在点第 N+1 下 →
   `element was detached from the DOM, retrying` → **整支用例挂死 13 分钟**。
   → 改成受保护点击：先判 `res`/`miniState==='done'` → `page.$()` 确认存在 → `try/catch` 吞超时。
3. **`page.evaluate` 不能返回 DOM 元素**（会序列化成普通对象）：
   `return el.closest('[data-mini-action]')` 外面再 `.getAttribute` → `TypeError: hit.getAttribute is not a function`。
   → 命中判定必须在页内取字符串再返回。
4. **循环要墙钟兜底** + 外层 `timeout 480 node ...` + 脚本内看门狗 `setTimeout(... 7min ... process.exit(3))`。
5. **C 段"整局能打完"必须重开一局**：C2~C6 的交互探针已经把开局那一步用掉了，
   接着跑要么抛"不在开局"，要么从已建好的中盘续（浮桥会卡在"已建的段点不动"，永远搭不满）。

### 真 bug ① 担架急送：`ellipse` 少一个参数 → rAF 链断 → 玩法永久冻在起点

`minigames-stretcher.js:328` 弹坑描边写成 `g.ellipse(x, GROUND+4, 15, 6, 0, Math.PI*2)`（**6 个参数，要 7 个**）
→ 第一帧 `draw()` 抛 `TypeError: ... 7 arguments required, but only 6 present`
→ `requestAnimationFrame` 再也不排。**画面画了一半所以"看着有画面"，dataset 恒为初始值，只是永远不结算。**

- `node --check` 语法正确；上一轮的**帧循环数值模拟**（纯逻辑）也验不出来 —— 渲染路径不在模拟里。
- **发现手法**：写了个"安静对局"诊断（只 boot + 每 700ms 读 dataset，不点任何键），
  一眼看到 `t=1s/6s 推进 0% 局内剩 90s` 不动；再挂 `pageerror` 监听拿到确切异常。
- 修完实测：`t=21s 推进 77.8% 失血 82%` → `0.15 / died`（一路抬着走必死）；点「放低」carry 1→0 ✓。

### 真 bug ② 夜搭浮桥：段行**每帧重建** → 自动化一段都点不进去（真人却没事）

`renderSegs()` 挂在每帧跑的 `sync()` 里，`segRow.innerHTML=''` **每秒重建 700+ 个节点**。
真人点击落在指针下的活动节点上没问题，但 `page.click` 拿到的节点下一帧就 detach
→ `Timeout 3000ms exceeded` → 桥一段搭不上 → 三局全 `exposed`、C4/C5/C6 全红。
**修法**：段行加签名守卫（只在 `segs/phase/alarmSeg/anchorSeg` 变了才重建）。
修完诊断里逐秒打点：挂灯 → 架满 12 段 → 渡河遇警加固 → 天亮前拆完 → **`score 0.75 / pass`（实耗 55s、断 1 次）**。

### 真 bug ③（QA 基建，影响所有用例）`browser.close()` 后紧跟 `process.exit()` → 进程永不退出

5 行脚本最小复现：只 exit ✓ / close 后立刻 exit **卡死**(EXIT=124) / close 后 `setTimeout(exit,300)` ✓。
**上一轮把这误判成"driver 挂死 13 分钟"，其实一大半是收尾顺序。**
五个用例统一改成：
```js
const finishExit = () => process.exit(bad ? 1 : 0);
setTimeout(finishExit, 4000);
browser.close().then(finishExit, finishExit);
```

## 第二轮（同日下半天）：四支玩法收敛到全绿

### 真 bug ④ · 担架急送换肩冷却**从来没上膛**（`SWAP_CD` 三处都在、没人赋值）

`SWAP_CD = 5.5` 导出着、`swapCd` 声明着、`b3.disabled = swapCd > 0 || swapLeft > 0` 绑着，
**唯独 `doSwap()` 里没有 `swapCd = SWAP_CD;`**。后果不是"少个冷却"：硬直一过（1s）立刻又能换肩
= **1 秒回 26 点体力** → 体力不是资源，决策③（什么时候换肩）整个作废。
**修法**：补赋值；顺手**直接改 `disabled` 属性**而不是调 `renderActs()`（重建节点会让正在进行的点击落到 detach 节点）；
帧循环里冷却归零那一帧要**再重画一次**，否则按钮灰了就不再亮。
**QA**：旧 C5（"点完 150ms 内 disabled"）**拦不住它** —— 1 秒硬直本来就够变灰。
改成三段式 `C5a 150ms 灰 / C5b 1.5s（硬直已过）仍灰 / C5c 到点真的放开`，加 `A6b SWAP_CD > SWAP_SEC`。

### 真 bug ⑤ · 夜搭浮桥**在数学上不可能通关**（设计算术错，不是代码错）

- 搭满 12 段 = 15 板（4 浅滩×1 + 5 船×1 + 3 中流排×2）；会晃的只有中流 3 段板排；
- 一段报警**要么被加固（→R，出局）、要么过窗没加固（→塌，出局）** → 全场报警 ≤ 3 → 最坏要 6 块加固料；
- 原 `PLANK_CAP = 18`，`18 − 15 = 3` → **只够加固一次半**，正确打法必沉。
- 更糟：原来"**搭满即自动渡河**" → 玩家越手快越没有余料，**手快只有坏处、且没有杠杆**。
- **修法**：`PLANK_CAP` 18→**24**、`PLANK_ARRIVE_EVERY` 5→**4**、到货上限判断只按 cap（原来那个
  `arrived*2+4 < CAP` 会提前断供）、**新增「部队上桥」动作**（`data-mini-action="cross"`/`Space`；
  桥没搭完 `disabled` 且**不挂** `data-mini-action`，所以 A7 的 15 不变、搭满后 +1→16）。
- 结果：B1 `0.85 / pass / 断0`，与手算 `0.6+0.1(灯)+0.15(无晃段)` 完全吻合；B2 不加固必沉、B3 拂晓暴露。

### 真 bug ⑥（驱动侧）· `playProper` 点空一次就 `break` → 桥永远搭不满

写死顺序 + `boatTo()` 只点一次：门板陆续到货，手里不够时那次点击是**合法空操作** →
见没进 `anchor` 就 `return false` → 外层 `break` → 再没搭过一段。
症状极其误导：**B1/B1b/B2/B4/C7/C9 六项一起红**，像玩法崩了。
真线索是 **C9 的状态序列 `rig/done/anchor` —— `cross` 从头到尾没出现**。
**修法**：驱动改成自适应（每轮重看"还缺哪段、手里几块料"，够就点、不够就等）。

### QA 基建 · 观测窗口 < 一次 Playwright 往返 → 整段搬进页面

`qa-grab` D5（张力条高位转红）连红四轮，实得恒 `高位 95 vs 低位 95`。
因：张力 `T_START=46`、**涨速 13/s** → "低位"窗口只有 1~2 秒；而往返一趟（`page.click` 三项可点性检查
＋一次 `evaluate`）几十到几百毫秒，等看到 `phase==='pull'` 张力**已经 86**。
**修法**：把「驱动 + 取样 + 等待」整段写进**一次 `page.evaluate`**（零往返），
驱动用元素自身 `.click()`（绕开可点性等待；"真点击"另由 C2~C4 负责）。
修完低位样本实得 36~52、色差 74，一次绿。

### 真 bug ⑥（设计层面）· 浮桥"不加固"这条失败线原来是**掷骰子**

材料经济调平后 B1 绿了，B2 还红，而且红成「未结算」（不加固也把部队送过河了）。查 `frame()`：

```js
if (alarmSeg < 0) { if (risky.length && rnd() < WOBBLE_RISK) { alarmSeg = …; } }   // 报警期间不掷骰
```
- 一次渡河只有 **约 11 秒**（`CROSS_RATE=0.092`），而一条"报警 + 4 秒窗口"吃掉 **4.9 秒**；
- 全场只够掷 **~3 次**骰 → `P(至少 2 次报警) ≈ 1 − 0.58³ − 3·0.42·0.58² ≈ 0.38`
  → **"不加固"有六成概率照样过桥**，而且 B4 的分数分叉也一起塌。

**修法**：`WOBBLE_RISK` 整个删掉（全仓只有这个文件用），改成**每次判定必报一段**（报哪一段随机）
→ 报警次数 = 晃段数 = 3（5 船全给中流且都掐在窗里时）→ 要 6 块加固料，封顶 24 有 9 块余量。
配套 QA：`B1c 这一局真的报了 ≥3 次警`（防随机性偷偷回来）；
B2 把**结果与原因一起断言**（`sunk` **且** 报警 ≥2 次），免得"只报一次警→没断→跑到拆桥→未结算"
被误读成玩法坏了。
顺带修：渡河到 100% 时若还挂着一条未处理的报警，红圈会被带进拆桥阶段且永不结算 → 转阶段时清 `alarmSeg`。

### "API 反应有点慢"——真因是僵尸请求雪崩（用户问："涉及 API 的玩法为啥慢"）

用当天日志 + 直接打网关定量查清，**不是"模型有点慢"，是自己把自己压垮**。

**当日日志统计（`logs/ai-calls-2026-09-16.jsonl`，29 次调用）**

| callType | n | 中位耗时 | 成功率 | prompt 字符 |
|---|---|---|---|---|
| school_quiz | 9 | **180.6s** | **2/9** | 1328 |
| school_lesson | 7 | 175.2s | 3/7 | 1462 |
| gomoku_move | 8 | 112.5s | 4/8 | 1042 |

（空 JSON ×3 / JSON 截断 ×1 / 缺字段 ×1）。

**直接打网关实测（同参数：glm-5.1 + `reasoning_effort:low` + max_tokens 2500）**

| 探针 | 结果 |
|---|---|
| A 极小请求（20 prompt token） | **200 / 9s** —— 网关空载地板就有 9 秒 |
| B 真实 gomoku_move | 200 / 21s / `completion_tokens 2455` / content 仅 284 字符 |
| C 真实 school_quiz | 200 / **83s** / `completion_tokens 2414` / content 689 字符，且**以 ```json 代码围栏开头** |

→ **推理 token 吃掉了绝大部分 max_tokens**（B：2455 token 只为选一个候选点 + 一句话），
常贴近 2500 上限 → 被截断 → 空 JSON / 解析失败 → 触发重试。

**真凶（代码级确认）**：`/api/decide` **没有把"客户端已断开"往下传** ——
`server/index.js` 里既没有 `req.on('close')`，也没把 AbortController 交给 `callGlm51`；
`server/ai.js` 里唯二的 `signal` 都是内部超时用的。于是：

1. 前端 `AI_WINDOW_MS = 10000`（用户定的窗口）10 秒就放弃；
2. 服务端**毫无察觉**，继续跑 `TIMEOUT_MS 90s`，失败后再 `MAX_RETRIES 2` 重试一次
   （`config.js` 自己注释写着"最坏 90s + 0.6s + 90s ≈ 181s"）；
3. 玩家"等不及 → 重试/继续"再发一批 → 后台僵尸请求越堆越多。
   **日志时间轴证据**：最后 100 秒内有 **10 个请求同时在路上**，每个 180s；
   而当天开头（t+0～t+1000）的调用只要 16–66s，**t+1600 之后几乎全变 180.6s 超时**
   —— 这种"越用越慢"的时间相关性就是队列积压，不是模型天生慢。

**附带限制**：这把 Key 在比赛网关上只有 `glm-5.1` 可用（`glm-5.3-flash`/`glm-4-plus`/
`glm-4-air`/`glm-4-flash` 全 403）→ **"换个快模型"这条退路当前不存在**。

**修法（已给用户，待其点头，未动手）**：① 断连传导（`req.on('close')` → `abort()` 上游），
消掉僵尸请求；② 超时类失败不重试（`AbortError` 直接返回，别 90×2）；
③ 结构化小任务（gomoku_move / school_*）单独设更小的超时与 max_tokens；
④ 前端 10s 窗口与服务端超时对齐，别一个 10s 放弃、一个跑 181s。

   = **板刚落地就白挨枪**。修法：`doLay()` 开头 `swapLeft = 0; stance = wantStance;`（扛板本来就走不了）。
2. **换挡期间 `stance` 绑定的是"旧目标"** → 中途松手要先等本次换挡结束、再排第二次换挡
   = 实际站住 **1.5 秒**、且角色先蹲回旧姿势再站起来，手感像卡住。
   修法：换挡期间每帧 `stance = wantStance`（落到"最后要的那个姿势"），不再叠第二次。

断言自己写错：A11 拿 `< 半桥` 判"必须挑"（设计其实是 `≤ 半桥`）· C2 想在 0.7 秒窗口里等到**整数折人**

（改在 70 米处取样）。

> **D8 连红两轮，根因是"采样时人跨了段"**，而且是我自己加的 `sleep(300)` 造成的：
> 玩家在 8.4 米处，段界在 8.5 米 —— 直起身 3.05 m/s，一帧就迈过去，于是"板铺在第 1 段、
